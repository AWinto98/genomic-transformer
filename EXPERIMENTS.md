## Status / next

- **2026-11-15 phase-3 verdict**: scaled MLM (5 ep, loss 1.2932->1.1722) + CTCF fine-tune **test AUROC 0.9633** (vs scratch 0.7981, pilot-MLM 0.7924); frozen probe 0.6486. The pilot's "neutral" was a 1-epoch artifact — pretraining works at this scale. Caveats: single seed; corpus included val/test sequences unlabeled. Next: seed-43 replicate (~$0.50), chromosome-held-out pretraining corpus for the strict number, then JUND-from-MLM5 with the small-data recipe question still open.

- Transformer > baseline confirmed (AUROC/AUPRC both splits). ACC ~tied.
- 2026-11-14 sweep (3 arms, one pod, ~87 min total): **`transformer_cloud-004` (d_model 256) is the clear winner** — val 0.8045 / test 0.8113 AUROC, early-stopped at ep 35 (best 27). Epoch scale-up (002) confirmed the curve was still rising at 20 ep (+0.013 test AUROC). lr 1e-3 (003) is strictly worse than 3e-4 — keep 3e-4.
- Not yet explored: build on 004 (d_ff 1024, longer patience, dropout/wd regularization — 004 peaked at ep 27 then flattened), motif interpretation (margin now large enough to matter), inference/scanning script (`docs/cloud-runbook.md` has the cloud workflow). Multi-seed for 004: DONE (3 seeds 42/43/44 — mean±std test AUROC 0.7981 ± 0.0138, see table above; seed 42 is the optimistic end, not a fluke-clearing outlier).
- 2026-11-14 phase-2 session (ONE pod `phase2`, 176 min ≈ $2.61): MLM pretrain on hg38 (1.5M windows, 1 epoch, flat 1.29 loss) + CTCF fine-tune from MLM (2 seeds: val 0.7565 / 0.7723, test 0.7922 / 0.7926) + JUND trio (all CHANCE-LEVEL). Headline: **MLM init does not beat scratch at pilot scale**, and **JUND does not train with the CTCF recipe at 13.6k windows** — next: diagnose JUND recipe (lr/schedule/model-size vs small data) before any more transfer runs; consider longer MLM (multi-epoch, larger corpus fraction) before re-testing init value. Code/configs/figure committed as 7a6e34c.
- 2026-11-14 JUND re-diagnosis (local log forensics, free): all five chance-level transformer runs were early-stopped within 1.3k–2.5k optimizer steps (JunD epoch = 212 steps at batch 64; patience 6–10 epochs ≈ 1.3k–2.1k steps). Transfer-init runs (esp. ctcf-init) were learning when killed; from-scratch arms sit at a constant-output saddle (train_loss ≈ ln2, moves <0.003 over 11 epochs even at lr 1e-4–3e-4), while a linear k-mer model gets 0.80 AUROC on the same arrays. Working hypotheses: (1) patience-in-epochs is mis-scaled for tiny datasets — post-transfer val AUROC wobbles for thousands of steps before climbing; (2) from-scratch cold-start on 13.6k windows is genuinely hard. Diagnostic DONE (pod `jund-p60`, 48.7 min ≈ $0.72, 3 arms, patience disabled): **patience was never the binding constraint.** ctcf-init overfits (train_loss → 0.013, val peaks 0.6064 @ ep 10 then declines to 0.584); mlm-init and scratch stay at the ln2 saddle all 60 epochs — scratch even at lr 1e-3 only reaches train_loss 0.686. **CONCLUSION: the JUND failure is a genuine generalization gap / inductive-bias mismatch** — on 13.6k windows the transformer either memorizes (transfer init) or stalls at a constant-output saddle (scratch/MLM-init), while a linear model on 2080 k-mer count features gets val/test 0.795/0.797 on identical splits. Next hypotheses if JunD is revisited: k-mer-count input features to the MLP head, much stronger regularization (dropout/wd), or a far smaller model; otherwise k-mer LR is the honest JunD answer at pilot scale.
